# Why Row Level Security gets its own controls

Supabase lets a web page talk straight to the database with a public key. That's what makes it fast to build on, and it's why **Row Level Security (RLS) is the security boundary**: the key is public by design, so the database rules are the only thing deciding who reads what.

When those rules are missing or too broad, data leaks without any hacking at all.

## What has gone wrong elsewhere

- **CVE-2025-48757** (published May 2025, CVSS 9.3): apps generated by the Lovable AI app builder shipped with Row Level Security policies that let remote, unauthenticated users read data. Researchers catalogued more than 170 affected live apps. Lovable disputes the CVE, saying each customer is responsible for protecting its own data.
- **UpGuard, "Everything Everywhere: Systemic Data Exposure in Supabase Apps" (2026):** from about 300,000 domains with Supabase indicators, UpGuard found **16,326 databases** with readable tables, and reported that **over half had indicators of personal information**. The causes it describes: tables with no RLS at all, policies that exist but don't restrict enough, and public keys used as if they were secret. It also notes that tables created through the API, which AI coding agents use, don't get RLS by default.

These were customer configuration mistakes, not breaches of Supabase itself. That's the shared responsibility model: Supabase secures the platform, and each customer must configure access correctly. Supabase has since made RLS the default for tables created in its dashboard.

## The three failure patterns, and what Risk Ledger does about each

| Failure pattern | Prevention | Detection |
|---|---|---|
| **A table with no RLS** | RLS turned on for every table at setup; default privileges revoke access on any new table | **SB-01** (live, daily): fails if any table in the public schema lacks RLS. Tested by creating a table without it |
| **RLS on, but a policy lets everyone in** (`using (true)`, "any signed-in user", or a policy for anonymous visitors). The CVE-2025-48757 pattern | Every policy checks the user's role, and owners are matched by ID. Anonymous visitors get no table rights at all | **SB-04** (live, daily): fails on any `true` policy, any policy that only checks someone is signed in, any policy for anonymous or public roles, or any table right granted to anonymous visitors. Tested with each pattern |
| **A secret key in the browser** | The web page uses only the publishable key. The secret `service_role` key, which bypasses RLS, is never in the repository or the page | The anonymous probe script refuses to run with a secret key |

## Testing it from the outside

The database tests (`tests/run.sh`) act as every role from the inside. [`scripts/anonymous-probe.sh`](../scripts/anonymous-probe.sh) does what the scanners did, from the outside: it takes only the project URL and the public key, then tries to read every table and call every function as an anonymous visitor.

```bash
sh scripts/anonymous-probe.sh https://YOUR-PROJECT.supabase.co sb_publishable_...
```

## A note on "members can read the register"

Some tables, such as risks and controls, are readable by every user who has been given a role. That's deliberate: in a GRC program, control owners and auditors need to see the register. The difference from the leaked apps is that **access depends on a role the system owner assigns**, so a stranger who signs up sees nothing. The sensitive tables (evidence, remediation, raw source data and the audit log) are limited further, by role and by ownership.
