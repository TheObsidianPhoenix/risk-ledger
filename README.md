# Risk Ledger

**Continuous control monitoring on Supabase: automated evidence from source systems, a risk register that shrinks as fixes land, and AI-drafted control tests a human approves.**

Built by Jasmine Alexander (GRC) for Obsidian Phoenix Labs, a demo company with fictional data. No screenshots: every piece of evidence is generated by a test, timestamped, and permanent.

## How it works

```
Source systems ──► Control tests ──► Evidence ──► Remediation ──► Risk register
(AWS, GCP, Okta,    (declarative      (permanent,   (owner, due      (ready to close
 HR, training,       rules, or live    timestamped)  date by          only when every
 vendors: mock;      checks of this                  severity)        control passes;
 Supabase: live)     database)                                        a person closes it)
                                    every change ──► hash-chained audit log
```

- **Thirteen controls** across nine source systems. Eight systems are **mock** data shaped like their real APIs (AWS, Google Cloud, Okta, Google Workspace, an HR system, security training, vendor management, a vulnerability scanner). **Supabase itself is live**: four checks read this database directly: Row Level Security on every table, **no policy that opens a table to everyone** (the pattern behind CVE-2025-48757), the audit log can't be altered, and GRC analysts use MFA.
- **Every control says how it lowers risk.** "How does this actually lower risk?" is the first question to ask about any control, so it's a required field.
- **A failed test opens remediation work** for the control's owner, due in 7 to 60 days by severity. **Only passing evidence can close it.** Nobody can mark a fix done by hand.
- **Risks follow their controls.** A risk becomes *ready to close* only when every linked control's latest evidence passes, and a GRC analyst closes it with a note. The trend view shows the register shrinking.
- **It runs every day by itself.** A scheduler inside the database runs every test daily, and a separate daily check from outside (signed in as the read-only auditor) fails loudly if the schedule ever stops.
- **Risk acceptance expires.** An accepted gap needs a reason and an end date within 180 days; after that, the next test run reopens it.

## The web page

[`web/`](web/) is a small, dependency-free page published on GitHub Pages. It signs in with Supabase Auth, asks for authenticator-app MFA, and has six views: **dashboard**, **controls**, an **evidence viewer**, **remediation**, the **risk register** with its trend, and the **audit history** with a one-click hash-chain check. What each person sees depends on their role, and the database (not the page) enforces it.

- Talks to Supabase's REST and Auth APIs directly with `fetch`, using only the **publishable key** and the signed-in user's token. No secret key exists anywhere in the page, and the publish step refuses to deploy one.
- A strict **Content Security Policy**: only its own files, no inline code or styles, and network calls only to Supabase.
- Text is always inserted as text, never as HTML. The login lives in `sessionStorage` and ends when the tab closes.

`tests/web/smoke.js` runs the page in a real browser against data dumped from the tested database: sign-in, a wrong password, MFA setup and a wrong code, every view, a remediation update, closing a risk, verifying the audit chain, light mode and phone width. It fails on any page error or security-policy violation. Both test suites run on every push before the page is published.

## Control tests are rules, not code

A test is a small JSON rule, such as "every Okta user marked privileged has `mfa_enabled = true`," evaluated by fixed, tested code. Six rule shapes exist: `all_match`, `none_match`, `percent_match`, `within_days`, `max_age_days` and `before_date`. A rule can only compare fields in collected evidence. It can never run SQL or code.

That's what makes **AI-drafted tests** safe: an assistant turns a plain-English request into a rule, the database **validates** it (known shape, safe field names, and a collection that actually exists in the evidence), it's saved as a **draft that never runs**, and a **GRC analyst approves it** before it becomes active. The approver is recorded.

## Security model

| Control | How |
|---|---|
| Least privilege by role | **GRC analyst** runs tests, approves controls, accepts and closes risks. **Control owner** sees and updates only their own remediation (progress and notes). **Auditor** reads everything, changes nothing. **New sign-ups get no access** until the system owner assigns a role |
| Row Level Security | On every table, deny by default. Two live controls watch it daily: SB-01 fails if a table without RLS appears; SB-04 fails if any policy allows every row, only checks that someone is signed in, or applies to anonymous visitors. See [why RLS gets its own controls](docs/why-rls-matters.md) |
| Workflow rules in the database | Guard triggers enforce them even if the web page has a bug: no closing remediation by hand, no closing a risk before its evidence passes, no activating a control without approval, acceptance capped at 180 days |
| Permanent evidence | Evidence and source snapshots can't be updated or deleted, even by the database owner |
| Tamper-evident audit log | Every change is logged with who, when and what changed. Each row carries a hash of the one before it; `verify_audit_chain()` finds any edited row. Updates, deletes and truncation are blocked |
| Minimal grants | Anonymous visitors get nothing. Signed-in users can read (as RLS allows) and update only three remediation columns and a few risk fields; everything else goes through checked functions. Every function pins its `search_path` |
| MFA | Supabase Auth with authenticator-app MFA; SB-03 fails while any GRC analyst lacks it |

## Tests

`tests/run.sh` builds the database on plain Postgres (with a small stand-in for Supabase's `auth` schema) and runs **100 checks** acting as each role: anonymous, pending, GRC analyst, two control owners and an auditor. They cover access control (including one owner trying to read another's work), workflow rules, evidence-driven closure, risk acceptance expiry, audit-chain tamper detection, AI-draft validation and the live checks. Removing a guard or a Row Level Security policy makes them fail.

```bash
PGHOST=/tmp PGPORT=54329 PGUSER=postgres ./tests/run.sh
node tests/web/smoke.js        # needs Playwright
```

From the outside, [`scripts/anonymous-probe.sh`](scripts/anonymous-probe.sh) attacks a live project with only its public key, the way the 2025 and 2026 scans of exposed Supabase apps did, and confirms every table and function refuses an anonymous visitor.

## Set up your own copy

1. Create a Supabase project.
2. Open **SQL Editor**, paste all of [`supabase/setup.sql`](supabase/setup.sql), and click **Run**. It runs as one transaction, so it either fully works or changes nothing.
3. Create users under **Authentication → Users**, then assign roles in the SQL Editor (see [`docs/setup.md`](docs/setup.md)).
